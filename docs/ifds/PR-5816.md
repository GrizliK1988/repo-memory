## Observed source changes

The original initializer obtains content-language preferences and joins them into
a string. The replacement calls a helper returning a projection of the app-language
preference. Both versions pass `contentLangs` into the first request's URL and
language header. The fallback request omits that URL parameter and uses an empty
language header.
[Original feed source](https://github.com/bluesky-social/social-app/blob/e9be8f4574ad5e2da145b24a2af4258fd4d7769a/src/lib/api/feed/custom.ts),
[modified feed source](https://github.com/bluesky-social/social-app/blob/5e006432b9e80555e5ebca90a99a920ddd605ed6/src/lib/api/feed/custom.ts).

The new helper reads `appLanguage`, splits it, and selects element zero. The
existing content-language getter remains present. The PR also adds a labeler header
object and spreads it into both requests' headers.
[Language helpers](https://github.com/bluesky-social/social-app/blob/5e006432b9e80555e5ebca90a99a920ddd605ed6/src/state/preferences/languages.tsx),
[PR diff](https://github.com/bluesky-social/social-app/pull/5816/files).

## Expected selected flow

The following is a semantic projection, not a claim about the concrete language
string or network response for any user:

```text
before:
  preferences.contentLanguages
    -> getContentLanguages return -> join
    -> contentLangs initializer
    -> first fetch URL's lang interpolation
    -> first fetch Accept-Language input

after:
  preferences.appLanguage
    -> split -> element 0 -> getAppLanguageAsContentLanguage return
    -> contentLangs initializer
    -> first fetch URL's lang interpolation
    -> first fetch Accept-Language input
```

Both final consumers independently depend on the initializer; the two arrows
listed after the initializer are separate outgoing branches, not a sequence from
URL to header. Origin traversal must respect the appropriate call/return contexts.

Expected distinctions:

1. The selected binding and its initialization site align across snapshots.
   The value-producing operation/source changes; a later reassignment is not
   required for this to be a meaningful data-flow change.
2. The first request's language consumers retain their direct use of `contentLangs`.
   Report changed upstream provenance, not a newly introduced use solely because
   line numbers or object formatting moved.
3. The old preference source stops contributing to the selected query. The old
   getter is not deleted from the repository; this is a slice-membership/flow
   change. The newly introduced helper is also an actual code addition.
4. The fallback request has no direct value dependency from `contentLangs` into
   its URL or language header in either version. These are required negative cases.
5. The new labeler data is an independent value flow. It must not be reported as
   a new origin of `contentLangs` or its language value merely because it shares
   a headers object. Proving that the spread cannot overwrite the language field
   requires its closed property set; otherwise report that boundary as uncertain.

The first request's response governs whether the fallback is attempted. Any claim
that changing `contentLangs` changes that response or fallback execution depends
on an external-service model and must be separated from proven request-input flow.
The initial oracle stops at request inputs. Later reports may show the response/
fallback control context with an explicit unknown network dependency, not assert a
new direct language-value edge to the fallback request.

This endpoint is a declared network-model boundary, not the end of the language
value's real-world effects. The full-flow report keeps both unchanged request-input
consumers, their paths from the changed origin, and `modeled_boundary` ending
records for the exact inputs. It must show that continuation through the external
service is open, even when the request-input slice is `complete_for_query` under
its models. Do not infer no later impact, and do not invent response dependencies
to make the graph appear complete. Retained consumer metadata can support later
comparison with historical consumer-side fixes without asserting a current bug.
